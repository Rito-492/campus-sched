## 2. M0：让所有人能开始的基础交付

M0不是等待整份需求文档签字才开始；本任务包已提供可实现的统一产品基线。六人可并行执行各自M0任务：

1. 项目经理建立后端构建、公共DTO/端口、统一错误处理及Clock bean，后端空业务测试可运行。
2. 设计师按契约一次建立完整V1 schema并通过迁移测试，不为每个模块建另一套数据库。
3. 配置经理建立db Compose、开发/测试配置、环境模板及种子导入器框架；测试经理提供数据格式和账号资源数据。
4. 界面设计师建立前端项目、路由、样式变量、网络客户端；UI页面先用明确标注的fixture进行组件开发。
5. 测试经理建立qa工程、DbTestSupport及固定Clock/隔离schema工具，交给后端各负责人。
6. 分析员按契约细化需求、状态转换用例及activity模块骨架，纯状态测试先行。

配置经理收集这些M0产物，项目经理检查一致性。M0完成标准：同一代码版本上后端可编译、数据库可迁移、前端可构建、测试支持可用、依赖版本锁定。记录真实commit或文件包版本，不伪造“已完成”标记。

依赖缺失时，先在本人目录完成record使用、纯逻辑和测试；替身仅放测试代码。缺少M0共享工程时不得自己生成另一套工程后整目录覆盖。交接单应明确“缺哪个文件/契约、谁提供”，而不是泛称“等别人完成”。

## 3. 集成顺序

| 里程碑 | 依赖 | 并行开发 | 可展示结果 |
|---|---|---|---|
| M0 基础 | 本任务包 | 六人基础任务 | 工程、schema、类型和验证入口一致 |
| M1 单模块 | M0 | PM认证；AN活动/报名；DS资源/调度；CM变更/通知；UI页面；测试自动化 | 各模块有真实代码与本模块测试，前端可用fixture审阅 |
| M2 初次预约 | M1中认证+活动+调度；通知基础服务 | UI接真API；QA联调 | 创建→审批→联合预约→开放报名，取消释放 |
| M3 改期主线 | M2；变更模块 | 工作人员确认、重新审批、切换、通知和审计 | 演示主线真实跑通，失败保护可验证 |
| M4 发布 | M3与关键验收通过 | 缺陷修复、UI打磨、报告、手册、打包 | 可复现运行的交付产品及课程材料 |

M1允许在单模块测试中Mock端口；M2/M3不允许用Mock服务冒充联调完成。项目经理整合，配置经理保存真实可复现版本，测试经理决定哪些测试已实际覆盖。

## 4. 仓库与交接

共同代码库采用main为可集成分支，各成员分支为 `work/<学号>-<模块>`。创建远程仓库、账号邀请、公开发布由成员按实际权限执行；本任务包不含不存在的仓库地址。尚无远程仓库时可交换patch或文件包，但必须带基准版本、变更清单和测试证据，由配置经理合并后重新分发统一版本。

分支固定为：冀项阳 `work/55230223-foundation`，冯玉琪 `work/22220314-activity`，黄方勇 `work/55230315-scheduling`，汤雨润 `work/55230316-qa`，杨瀚霖 `work/55231031-change`，杨畅 `work/17231018-ui`。配置经理在共同工程目录核对是否已有Git仓库，确实没有时初始化一次 `git init -b main`；其他成员从该基准取得代码，不各建无共同历史的仓库。

每轮开始获取最新基准；提交只包含自己的改动，不把别人的未完成修改一起提交。合并冲突由对应所有者核对，禁止一律选择ours/theirs。共享契约变更由项目经理协调，设计师审数据影响，测试经理更新验证，UI同步字段。

每个岗位维护 `docs/<本岗位目录>/handoff.md`，固定格式：

```markdown
## 本次交付
- 成员、学号、任务ID：
- 基线：v2.0；基准commit/包版本：
- 交付文件与接口：
- 实际运行命令与结果：
- 验收编号与证据路径：
- 未完成项/外部依赖及负责人：
- 下一接收人及其动作：
- 接收确认：尚未接收（仅真实收到反馈后更新）
```

“基准commit/包版本”等运行时信息由执行agent填写真实值；不能为了填满模板虚构结果。

## 5. 环境、命令与发布归属

端口：web开发5173、API8080、PostgreSQL5432；Docker演示入口8088，默认绑定127.0.0.1。Compose固定项目名campus-events，避免中文文件夹名成为无效项目名。Vite将 `/api` 代理到8080，Nginx在演示环境代理到server:8080。浏览器不直接访问数据库。

环境变量固定：DB_HOST、DB_PORT、DB_NAME、DB_USERNAME、DB_PASSWORD、TEST_DATABASE_URL、TEST_DB_USERNAME、TEST_DB_PASSWORD、DEMO_DATE、DEMO_PASSWORD、APP_DEMO_SEED、APP_TEST_NOW。APP_TEST_NOW仅e2e profile读取，固定值由测试契约给定；非e2e应用必须使用真实Clock。测试环境可组合dev,e2e启用测试数据导入与固定Clock，DB_NAME必须campus_test。`.env.example`写说明与示例非秘密值，`.env`不入库。

每台机器先检查java -version、node --version、docker info；缺运行时则记录具体缺口并先做不依赖它的任务。配置经理提供 `scripts/load-env.ps1`，把本地.env的白名单键加载到当前进程环境，只解析键值，不执行文件内容。Compose会读.env，但直接运行Maven不会自动读，因此以下加载步骤不可省略。

```powershell
# M0之后开发启动；三个终端分别运行所需服务。
. ./scripts/load-env.ps1
docker compose up -d db
./server/mvnw.cmd -f server/pom.xml spring-boot:run "-Dspring-boot.run.profiles=dev"
npm --prefix web run dev

# 演示发布：配置经理完成Dockerfile、Nginx、环境读取后可用。
docker compose up --build -d
```

db首次初始化创建campus_dev与campus_test，生产业务账号不拥有随意清理测试以外库的脚本权限。数据库备份与迁移步骤写入发布说明；禁止通过删除volume来掩盖迁移失败。

M0负责提供Maven Wrapper、POM的Surefire/Failsafe规则；UI提供web的dev/typecheck/test:unit/build脚本；测试经理提供qa的test:e2e/evaluate脚本及Playwright配置；配置经理提供check.ps1统一调用。没有脚本或测试不存在时检查必须失败，不能直接返回0。

E2E使用配置经理提供的独立compose.qa.yaml：项目名campus-events-qa、独立数据卷、数据库宿主端口5440、API宿主8081、web宿主8089，容器内部端口仍为5432/8080/80；服务端dev,e2e、DB_NAME=campus_test、APP_TEST_NOW与DEMO_DATE按验收规范固定，BASE_URL=http://127.0.0.1:8089。启动命令：`docker compose -p campus-events-qa -f compose.qa.yaml up --build -d`。该文件完整声明测试服务，不与开发Compose叠加端口数组。测试完成保留失败证据；清理仅针对该测试项目，不能清理开发环境卷。

## 6. 每个开发任务的执行方式

阅读本岗位任务后按编号执行：先根据验收场景写能证明边界的测试→运行并确认尚未实现时失败→实现最小完整行为→运行测试及构建→更新对应课程文档→交接。普通文案和样式小改不强制镜像测试，关键状态、并发、事务和权限必须有验证。

首次允许创建本岗位缺失目录；已存在代码则先读再改。若框架或命令和基线冲突，报告具体差异并请求统一，不悄悄换语言。不要为没有提供的学校规则自行捏造事实，系统演示按本基线执行即可。

## 7. 文件包的分发方式

给每个人发送同一份包含根 `taskbook.md` 和完整 `agents/` 的任务包即可启动，公共契约已包含必需课程背景，不强制读取原电脑上的绝对路径或隐藏历史记录。每人只执行自己学号的文件，公共文件一起保留。后续代码通过共同仓库同步。

若任务包解压在工程子文件夹，先将taskbook.md及agents放到实际仓库根目录，或明确告诉agent真正的代码根目录。所有计划路径均相对于代码根目录，禁止在六个不同子目录分别创建六个独立产品。
