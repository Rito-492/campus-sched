# 开发基线 v2.0

适用项目：面向校园活动的多资源协同调度与变更影响分析系统。日期：2026-09-25。

本文和同目录其他契约是本轮为“六人分别使用agent开发”制定的统一实现方案。学校实际制度、团队能力、工期尚未得到证实；下述业务规则是课程演示系统的产品规则，不冒充本校规定。执行本任务包时统一采用它们，后续改变须同步契约及受影响模块。

## 1. 成品边界

实现一个可在浏览器操作、能持久化数据的Web应用。首版必须跑通：创建活动→教师审批→资源联合确认→开放报名→申请改期→冲突及替代方案→工作人员确认→重新审批→资源确认并原子切换→站内通知及记录。

首版必须有：五类用户权限、活动审批、场地和器材、联合预约、冲突解释、有限范围替代方案、改期影响、工作人员确认、限额报名/退出、故障影响、取消释放、站内通知及审计。候补、签到、归还验收、通用任务看板及统计报表本期不实现；不接校园身份、短信、支付或硬件。不做自动人员排班，不承诺全局最优。

六个课程岗位同时承担明确的开发模块，见总说明。每人交付代码、验证证据及本岗位课程文档；不能只产出计划或空页面。

## 2. 统一技术方案

| 层次 | 本任务包采用的方案 | 约束 |
|---|---|---|
| 后端 | Java 21、Spring Boot 3.5.16、Maven 3.9系列 | 单体应用按业务包拆分，根包 `com.campus.events` |
| 数据访问 | Spring JDBC / JdbcTemplate、Flyway、PostgreSQL 17 | 显式SQL和事务；不混用JPA、MyBatis或另一数据库 |
| 安全 | Spring Security、BCrypt、数据库持久化的不透明登录令牌 | 不自行实现密码加密；不接SSO |
| 前端 | Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus | Composition API；自定义设计变量及核心交互，中文界面 |
| 前端运行时 | Node.js 22系列，至少22.18.0；npm | M0固定具体版本并提交 `package-lock.json`，其他成员用 `npm ci` |
| 验证 | JUnit 5、Spring Boot Test、真实PostgreSQL集成测试；Vitest、Playwright | 并发与事务测试不能用H2或纯Mock替代数据库 |
| 部署 | Docker Compose：db、server、web（Nginx） | 一个演示实例；浏览器访问web，同源 `/api` 反向代理server |

M0的脚手架负责人选择上述系列内兼容的依赖补丁版本，写入版本清单、POM和锁文件；这是明确的启动任务，不能让六个人分别升级依赖。后续只由对应构建文件负责人统一变更。

Java21与本Boot版本的兼容依据见[Spring官方要求](https://docs.spring.io/spring-boot/3.5/system-requirements.html)；前端运行时依据[Vue官方快速开始](https://vuejs.org/guide/quick-start)。本选择用于统一开发，不声称是唯一能做出精致界面的技术组合。

## 3. 软件角色与数据范围

一个校园，多组织。账号可有多个角色，但每次权限由后端检查。

| 角色枚举 | 允许范围 |
|---|---|
| STUDENT | 查看全校OPEN活动及本人参与的历史活动；报名/退出；读取自己的通知；本人被指定为工作人员时确认变更 |
| ORGANIZER | 创建活动，仅编辑/提交/取消自己拥有的活动；查看自己活动名单；选择方案和发起改期 |
| TEACHER | 审批本组织活动及改期；不能审批自己作为组织者的活动 |
| RESOURCE_ADMIN | 管理本校园资源、故障；确认联合预约及改期资源；只为这些职责读取活动与受影响名单 |
| SYS_ADMIN | 创建账号、赋予角色、停用账号；不自动拥有教师或资源审批权限 |

所有活动详情、名单和变更详情均需校验角色与归属，不能只在前端隐藏按钮。资源日历中无权查看的活动只显示“已占用”、资源及时间，不泄露名称、组织者和名单。未登录返回401，已登录但越权返回403，确实不存在返回404。

## 4. 数据与时间规则

- ID为UUID字符串；时间API使用带时区的ISO8601，后端转Instant，数据库用timestamptz，页面统一Asia/Shanghai。
- 活动只使用一个主场地和一个连续时段。活动时长30分钟至6小时；时间精确到分钟；布场、撤场各0至120分钟。
- 占用区间为 `[startAt-setupMinutes, endAt+teardownMinutes)`，包括布撤场。整段占用必须落在同一个上海自然日、资源每日开放区间之内；初始资源开放08:00—22:00。
- `expectedAttendees >= registrationCapacity >= 1`；场地容量不少于expectedAttendees。工作人员列表为本组织启用账号，去重；组织者可在列表内，但不需要向自己确认改期。
- 器材按资源池数量管理。数量为正整数；计划内同一资源只能出现一次。资源有category，同category可替换，替换保持所需数量。
- 场地同一时刻最多一个活动；器材同一时刻的所有ACTIVE预约数量加新需求不得超过“库存减该时刻故障数量”，可用数量下限为0。
- 区间端点相接不冲突。不能把彼此不同时发生、但都与长区间相交的预约简单求和。按开始/结束边界扫描同时需求；相同时间先处理结束再处理开始。
- 首版资源容量、库存、开放时间创建后不可编辑；后续不可用通过故障记录表达，避免另一条修改入口破坏容量约束。资源名称与类别也先不开放修改。

## 5. 活动状态与首次预约

| 当前状态 | 操作及角色 | 成功后 |
|---|---|---|
| 无 | ORGANIZER创建 | DRAFT，版本1 |
| DRAFT | 活动所有者编辑 | 新建不可变版本n+1，仍DRAFT |
| DRAFT | 活动所有者提交 | PENDING_TEACHER，不占资源 |
| PENDING_TEACHER | 本组织TEACHER同意 | APPROVED_UNRESERVED，不占资源 |
| PENDING_TEACHER | 本组织TEACHER驳回 | DRAFT，保存意见 |
| PENDING_TEACHER或APPROVED_UNRESERVED | 活动所有者撤回 | 克隆当前内容为n+1，DRAFT，旧审批不再有效 |
| APPROVED_UNRESERVED | RESOURCE_ADMIN确认 | 再检查并整组预约，SCHEDULED，设置effectiveVersionNo |
| SCHEDULED | 活动所有者开放报名 | OPEN，必须未开始且无资源风险 |
| 非CANCELLED且活动尚未开始 | 活动所有者取消 | CANCELLED，释放全部ACTIVE预约、作废待处理改期、取消有效报名并通知 |

资源冲突时首次确认返回409，状态保留APPROVED_UNRESERVED，无任何部分占用。编辑只允许DRAFT；SCHEDULED/OPEN的时间、场地、器材调整必须经过改期流程。首版改期不改变活动名称、人数、报名容量或工作人员。

## 6. 改期状态与影响确认

只有活动所有者能为尚未开始的SCHEDULED/OPEN活动发起改期，目标开始时间必须在当前时间之后。每个活动最多一个待处理改期。新建或编辑草稿的目标时间也必须在未来；报名/退出只允许OPEN且活动尚未开始。

1. 预览：只计算可行性、替代方案与影响，不写预约，不表示占位。
2. 创建：锁活动，校验baseVersionNo和expectedLockVersion，保存不可变targetPlan及影响快照。工作人员中除组织者外的人均需确认；没有这些人则直接PENDING_TEACHER，否则AWAITING_CONFIRMATIONS。
3. 确认：指定工作人员各自同意或拒绝。任一拒绝→REJECTED；全部同意→PENDING_TEACHER。同一人重复同意不重复推进。
4. 教师审批：同意→PENDING_RESOURCE；驳回→REJECTED。审批绑定changeId与targetPlan，不能被其他方案复用。
5. 资源确认：锁活动及改期，再按资源ID顺序锁新旧全部资源；重新检查。可行时同一事务写新活动版本、释放旧预约、建立新预约、将改期标为APPLIED并写通知事件。活动保留原SCHEDULED或OPEN状态。
6. 已失去可行性：不修改活动版本与旧预约，将改期标为CONFLICTED并返回409及冲突。组织者需重新预览并创建新的改期；已有教师意见不能移用。
7. 组织者撤销待处理改期→WITHDRAWN。活动取消→CANCELLED_BY_ACTIVITY。数据库异常→整个事务回滚，改期保留原待处理状态，可使用原请求重试。

待处理状态仅为AWAITING_CONFIRMATIONS、PENDING_TEACHER、PENDING_RESOURCE。这些状态期间冻结报名与退出，返回409 CHANGE_PENDING，确保影响名单不漂移；终态解除冻结。取消活动始终可以覆盖待处理改期。

参与学生收到改期通知，不作为本期必须同意的对象；工作人员同意与通知已读是两个独立动作。原资源本身故障时保留原记录并展示AT_RISK，不能把“未改动原安排”说成“原场地仍可使用”。

## 7. 冲突解释与方案搜索

冲突类型：VENUE_CAPACITY、OUTSIDE_HOURS、VENUE_OCCUPIED、EQUIPMENT_SHORTAGE、RESOURCE_FAULT。每条提供resourceId、资源名称、冲突区间、需求、可用数量、原因；无权限时不返回其他活动身份。

固定搜索范围：目标开始时间的 `[0,-30,+30,-60,+60,-90,+90,-120,+120]` 分钟偏移；保持活动时长和布撤场；候选场地按UUID升序。器材组合为原组合，以及“只替换一条器材需求为同category另一资源池”的组合，不做多行同时替换。循环顺序为偏移→场地→器材组合，原组合优先，替换组合按被替换resourceId再新resourceId升序。替换不能导致同一计划重复resourceId。先按上述顺序生成，最多检查300个完整组合；过滤过去时间及不满足硬约束的组合，去重，返回前5个可行方案。

排序为元组升序：`(abs(timeShiftMinutes), venueChanged?1:0, replacedEquipmentLines, startAt, venueId, 按resourceId排序的器材JSON)`。响应给出代价前三项、evaluatedCount、truncated和搜索范围；0个结果只表示该范围未找到方案。人工可输入范围外目标重新预览。

对照策略使用相同输入、候选集合、硬约束和300个预算，按生成顺序选择首个可行方案；比较成功情况、代价元组及耗时，不预设先进策略成功率一定更高。

## 8. 事务、幂等与故障

- 所有预约、释放、改期、取消必须经过统一SchedulingPort。资源行锁统一排序，不能仅锁“当前已有预约”，因为资源空闲时可能没有预约行可锁。
- 使用PostgreSQL READ COMMITTED事务：活动写入先锁活动，涉及改期再锁改期，最后依UUID顺序锁新旧资源并重新查询。资源故障只锁资源、写故障并查询影响，不反向锁活动，避免形成相反锁顺序。
- 写操作通过CommandExecutor在同一事务内处理Idempotency-Key；相同用户、key、路由和请求体重复时返回原结果，不能先因旧expectedLockVersion报错。key被不同内容复用返回409。
- 业务预期冲突可作为CommandResult返回并提交相应CONFLICTED记录；数据库异常必须抛出并回滚，不能捕获后假装成功。
- 审计与通知outbox跟随业务事务写入；通知处理器每2秒消费一批，按eventId+recipientId唯一去重，失败重试，失败通知不回滚已提交安排。
- 资源故障以带起止时间和unavailableQuantity的记录表示；venue数量只能为1。影响清单从当前预约计算，不自动删除预约或强制改期。

锁行为参考[PostgreSQL官方锁说明](https://www.postgresql.org/docs/17/explicit-locking.html)。具体共同方法、表和接口见[数据与接口契约](02-数据与接口契约.md)。
