## 1. 引言

### 1.1 目的

本文规定本项目在整个生命周期内的配置管理方法，用于：

- 识别需要纳入受控管理的配置项（代码、文档、数据、图源、环境配置等）；
- 约定配置库结构、分支策略、基线与版本号规则；
- 约定配置项变更的申请、评审与实施流程；
- 约定备份、发布与恢复方式。

目标：保证任何时刻都能追溯"谁在哪个基线之后改了哪个配置项"，并保证最终交付的产品可复现、可验证。

### 1.2 适用范围

适用于本项目全体成员、全部配置项（见 §3），覆盖从项目启动到最终交付（M0–M4）的全程。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| 配置项（CI） | 纳入配置管理、有独立标识和版本的单元（一份代码模块、一份文档、一个数据文件等） |
| 基线（Baseline） | 某里程碑时刻对一组配置项的冻结快照，用 tag 标识；进入基线后变更须走变更流程 |
| 配置库 | 存放全部配置项的受控仓库（本项目为 Git 仓库） |
| 变更控制 | 对已进入基线的配置项的修改申请、评审、批准与实施 |

## 4. 配置库管理

### 4.1 配置库

- 远程仓库：GitHub `Rito-492/campus-sched`（公开）。
- 本地仓库：成员通过 `git clone` 获取完整历史；以 `main` 为可集成分支。
- 配置库同时承担课程"配置库"交付物（任务包 §6 交付物 10）的角色。

### 4.2 分支策略

| 分支 | 用途 |
|---|---|
| `main` | 可集成分支，只接受经集成验证的合并 |
| `work/<学号>-<模块>` | 成员个人开发分支，六支预建：`work/55230223-foundation`、`work/22220314-activity`、`work/55230315-scheduling`、`work/55230316-qa`、`work/55231031-change`、`work/17231018-ui` |

规则：

- 每轮开始先 `git fetch` 获取最新基准；提交只含自己的改动。
- 合并冲突由对应模块所有者核对，禁止一律选择 ours/theirs。
- 缺陷修复在对应模块分支上进行。

### 4.3 提交信息

格式：`feat|fix|docs|test|model: 摘要`；涉及缺陷时引用 GitHub Issue 编号，如 `fix: 修复并发预约重复提交 (#23)`。

## 5. 基线与版本管理

### 5.1 基线命名

`baseline/<类型>-v<主>.<次>`，例如 `baseline/init-v1.0`、`baseline/requirements-v1.0`、`baseline/release-v1.0.0`。

### 5.2 基线计划

| 基线 | 触发时机 | 状态 |
|---|---|---|
| `baseline/init-v1.0` | 任务包并入仓库、仓库结构定型 | 待补登（见 §8） |
| `baseline/requirements-v1.0` | 需求规范评审通过 | 待建立 |
| `baseline/design-v1.0` | 设计文档评审通过 | 待建立 |
| `baseline/release-v1.0.0` | 最终交付 | 待建立 |

### 5.3 版本号规则

- 文档：`v<主>.<次>`，评审冻结后重大改动升主版本、小改动升次版本。
- 交付包：`v<主>.<次>.<修订>`。
- 二进制文档（docx/xlsx/drawio/png）无法行级 diff，修改已评审版本时另存新版本文件或在文档内维护版本记录，不静默覆盖。

## 6. 变更控制

对已进入基线的配置项，变更流程如下：

1. **申请**：变更人提出申请（飞书或 GitHub Issue），说明变更对象、原因、影响范围。
2. **登记**：配置经理登记到变更记录，评估受影响配置项。
3. **评审**：涉及交付物范围的变更由项目经理参加评审；涉及任务包契约的走《02 数据与接口契约》§7 跨模块修改规程。
4. **实施**：评审通过后由变更人实施，配置经理核对并更新基线（重新打 tag）。
5. **记录**：配置经理更新《配置项索引》与基线清单。

红线：已进入基线的文档不得直接覆盖或重写；不得绕过变更流程改写他人负责的已评审文档。

## 7. 环境、备份与发布

### 7.1 环境

- 开发环境通过 Docker Compose 提供（`compose.yaml`），固定项目名 `campus-events`。
- 端口：web 开发 5173、API 8080、PostgreSQL 5432、Docker 演示入口 8088（默认绑定 127.0.0.1）。
- E2E 使用独立 `compose.qa.yaml`：项目名 `campus-events-qa`、数据库宿主 5440、API 宿主 8081、web 宿主 8089。
- 环境变量模板见 `.env.example`；`.env` 不入库（已列入 `.gitignore`）。
- 环境变量加载脚本 `scripts/load-env.ps1` 只解析白名单键，不执行文件内容。

### 7.2 备份

- 数据库备份与迁移步骤写入发布说明；不通过删除 volume 掩盖迁移失败。
- 代码与文档以 Git 远程仓库作为主要备份；关键基线打 tag 留存。

### 7.3 发布

发布产物集中于 `release/`，包含可运行包、`README.md`（发布说明）与 `manifest.json`（真实代码/文档/测试版本与校验值）。发布时打 `baseline/release-*` tag。
