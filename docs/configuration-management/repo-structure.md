# 仓库结构与目录指南（repo-structure）

> **用途**：回答"什么东西放在哪里"。每个目录的定位、放什么/不放什么、命名示例，以及一张"该放哪"路由表。
> **读者**：全体成员（人类）与 AI agent。人类从 `README.md` 进入，agent 从 `AGENTS.md` §6 进入，都指向本文件。
> **维护**：配置经理（杨瀚霖）维护。**新增/移动/重命名/删除任何目录都是配置项变更**：走变更流程 → 更新本指南 → 同步 `AGENTS.md` §6 总览树。
>
> 版本：v0.1（2026-09-25）

## 1. 设计原则（为什么这样组织）

1. **按交付物组织**：`docs/` 的子目录与课程考核的 11 项交付物一一对应——评审和提交时按目录取文档，不用翻找。
2. **单一职责**：每个目录有明确的"放什么/不放什么"，见 §3。
3. **目录英文、文件中文**：目录名英文小写 kebab-case（工具与 Git 友好，避免中文路径的编码兼容问题）；课程下发文档保留中文原文件名（提交课程时必须与要求一致），新增文档用"类型-主题-版本"中文命名。
4. **源与产物分离**：可编辑源文件（`.drawio`）放 `models/`，随文档评审的导出产物（png/pdf）与文档放 `docs/` 对应目录；Figma 源在仓库外，只导出到 `docs/prototypes/`。
5. **活文档与冻结文档分离**：`.md` 是持续维护的"活文档"（本指南、`task-assignments.md`，可直接 diff、直接改）；`.docx/.xlsx` 是评审后版本冻结的交付物（无法行级 diff，改版本 = 另存新文件名）。
6. **骨架先行**：未启用的目录用 `.gitkeep` 占位，目录结构在 P0 就定型，后继产物按位置归位，避免"先乱放后搬家"。

## 2. 总览

```text
campus-sched/
├── AGENTS.md / README.md / .gitignore   # 仓库元文件（仅此三件，不新增，见 §3.4）
├── docs/        # 文档区：9 个子目录，对应课程交付物（见 §3.1）
├── models/      # 模型区：Drawio UML 源文件，按图类型分子目录、按需创建（见 §3.2）
├── src/         # 代码区：产品源代码（技术栈待定，见 §3.3）
├── tests/       # 测试区：测试代码与测试数据
└── scripts/     # 脚本区：构建/导出/校验等辅助脚本
```

## 3. 目录详解

### 3.1 `docs/` — 文档区

**总规则**：只放文档与文档伴生的导出产物；不放源代码（→ `src/`）、不放 `.drawio` 源文件（→ `models/`）。

| 目录 | 定位 | 对应考核交付物 | 负责人 |
|---|---|---|---|
| `docs/course/` | 课程下发的管理文档 | —（过程依据，不评审） | 只读，全员 |
| `docs/course/role-confirmations/` | 六份成员角色确认表（含上/下游交接关系） | — | 只读，全员 |
| `docs/planning/` | 计划族 | 初始/详细软件项目计划 | 项目经理 |
| `docs/requirements/` | 需求族 | 软件需求规范 | 系统分析员 |
| `docs/design/` | 设计族 | 设计文档 | 设计师 |
| `docs/prototypes/` | 原型族 | 用户界面原型 | 界面设计师 |
| `docs/testing/` | 测试族 | 测试计划、测试设计、测试报告 | 测试经理 |
| `docs/configuration-management/` | 配置族 | 配置管理计划 | 配置经理 |
| `docs/delivery/` | 交付族 | 用户手册、发布说明 | 界面设计师 / 配置经理 |

各目录细则：

**`docs/course/`**
- 放：课程下发的选题、分工、工具、考核等管理文档（现有 4 份）
- 不放：任何成员自产文档
- 命名：**保留原文件名，永不改名、不改内容**（红线，见 `AGENTS.md` §7）

**`docs/planning/`**
- 放：初始/详细软件项目计划、任务分解（WBS）、风险清单、进度记录、`task-assignments.md`（岗位任务分配基线）
- 不放：个人周报之类的零散记录（进飞书，季度性汇总再入库）
- 命名示例：`初始软件项目计划-v1.0.docx`、`任务分解WBS-v1.0.xlsx`、`风险清单-v1.1.xlsx`

**`docs/requirements/`**
- 放：软件需求规范（SRS）、用例规约与补充规约、业务规则、验收标准、需求追踪矩阵、需求变更记录
- 不放：用例图的 `.drawio` 源文件（→ `models/use-case/`）；原型截图（→ `docs/prototypes/`）
- 命名示例：`SRS-软件需求规范-v1.0.docx`、`UC-多资源联合预约-v1.0.docx`、`需求追踪矩阵-v1.0.xlsx`

**`docs/design/`**
- 放：设计文档（子系统、类、接口、数据模型、用例实现）、设计决策记录、设计变更记录
- 不放：UML 的 `.drawio` 源文件（→ `models/` 对应子目录）；设计文档中引用的导出图随文档存这里
- 命名示例：`DD-设计文档-v1.0.docx`、`接口定义-v1.0.docx`

**`docs/prototypes/`**
- 放：Figma 导出的原型图（png/pdf）、原型评审记录、**界面规范与页面流程**（杨畅的配套交付物，归原型族），**按迭代分子目录**
- 不放：Figma 源文件（在仓库外）
- 结构示例：`docs/prototypes/iter-1/资源日历.png`、`docs/prototypes/iter-1/原型评审记录-iter-1.docx`

**`docs/testing/`**
- 放：软件测试计划、软件测试设计（用例集）、测试报告、测试数据说明、缺陷统计
- 不放：可执行的测试脚本与测试数据文件（→ `tests/`）；Gitee issue 内容（在仓库外，报告里引用编号）
- 命名示例：`TP-软件测试计划-v1.0.docx`、`TD-测试设计-v1.0.xlsx`、`TR-测试报告-v1.0.docx`

**`docs/configuration-management/`**
- 放：配置管理计划、配置项清单、基线清单、变更记录、发布说明、本指南（`repo-structure.md`，活文档例外）
- 不放：其他岗位的文档"暂存"（各归各位）
- 命名示例：`CMP-配置管理计划-v1.0.docx`、`基线清单-v1.0.xlsx`、`变更记录-2026-10.md`

**`docs/delivery/`**
- 放：最终交付物——用户手册、发布说明/版本说明（面向课程验收的成品）
- 不放：过程稿（成品文档评审前的版本留在所属目录，如手册过程稿在 `docs/prototypes/` 评审记录中）
- 命名示例：`用户手册-v1.0.docx`、`发布说明-v1.0.docx`

### 3.2 `models/` — 模型区（Drawio UML 源文件）

| 子目录 | 图类型 | 主要产出阶段 | 主要负责人 |
|---|---|---|---|
| `use-case/` | 用例图 | P2 需求 | 系统分析员 |
| `class/` | 类图 | P3 设计 | 设计师 |
| `sequence/` | 时序图（用例实现） | P3 设计 | 设计师 |
| `activity/` | 活动图（业务流程） | P2–P3 | 系统分析员 / 设计师 |
| `state/` | 状态图（活动/预约状态流转） | P3 设计 | 设计师 |
| `deployment/` | 部署图 | P3–P4 | 设计师 |

子目录**按需创建**：首次产出某类图时 `mkdir` 即可（去处已由上表约定）；当前已建 `use-case/`、`activity/`（P2 即用），其余四个待 P3 首次产出时创建。

- 放：`.drawio` 可编辑源文件 + **同名导出图片**（如 `use-case/活动审批.drawio` + `use-case/活动审批.png`）
- 不放：只给某份文档用的临时截图（随文档放 `docs/` 对应目录）
- 命名：`<主题>.drawio`，主题用中文短语；导出图片与源文件同基名
- 版本：图随所属文档基线走，重大修改时另存 `-v2.0` 或在指南与基线清单中登记

### 3.3 `src/` `tests/` `scripts/` — 代码区（占位，技术栈待定）

- `src/`：只放产品源代码。**测试代码不放这里**。技术栈确定后由配置经理按框架惯例细化子结构（届时更新本指南）
- `tests/`：测试代码 + 测试数据（fixture/数据文件可放 `tests/data/`）。与 `docs/testing/` 的分工：这里放**可执行**的，那里放**给人评审**的
- `scripts/`：构建、导出（drawio/png 批量导出）、校验等辅助脚本，任何人可提交，配置经理审核
- 不放：IDE 生成物、依赖目录、构建产物（`.gitignore` 已排除，别手动提交）

### 3.4 根目录

只放仓库级元文件：`AGENTS.md`（agent 约定）、`README.md`（项目名片）、`.gitignore`。
**不新建任何顶层目录或顶层散文件**——有需求先查 §4 路由表，找不到再找配置经理走变更。

## 4. "该放哪"路由表（速查）

| 你手里的东西 | 去处 |
|---|---|
| 课程下发的表/模板/说明 | `docs/course/`（原文件名） |
| 项目计划、WBS、风险/进度记录 | `docs/planning/` |
| 需求规范、用例规约、业务规则、验收标准 | `docs/requirements/` |
| 用例图 / 类图 / 时序图 / 活动图 / 状态图 / 部署图的 `.drawio` | `models/<图类型>/` |
| 设计文档、接口/数据模型说明 | `docs/design/` |
| Figma 导出的原型图、原型评审记录 | `docs/prototypes/<迭代名>/` |
| 测试计划、测试设计、测试报告 | `docs/testing/` |
| CM 计划、基线/配置项/变更记录、结构指南 | `docs/configuration-management/` |
| 用户手册、发布说明（成品） | `docs/delivery/` |
| 产品源代码 | `src/` |
| 可执行测试代码与测试数据 | `tests/` |
| 构建/导出/校验脚本 | `scripts/` |
| 拿不准 | 先查本表 → 再查 `AGENTS.md` §4 交付物对照 → 仍不确定就问配置经理，**不要自创目录** |

## 5. 命名规范速查

| 对象 | 规范 | 示例 |
|---|---|---|
| 目录 | 英文小写 kebab-case | `configuration-management/` |
| 课程下发文档 | 原文件名，不改 | `项目组选题说明.docx` |
| 新增文档 | `<类型>-<主题>-v<主>.<次>.<扩展名>` | `SRS-软件需求规范-v1.0.docx` |
| 活文档（.md） | 英文 kebab-case | `task-assignments.md` |
| 原型导出 | `docs/prototypes/<迭代名>/` | `iter-1/资源日历.png` |
| Drawio | `<主题>.drawio` + 同名 `.png` | `class/预约控制器.drawio` |
| 分支 / tag / 提交信息 | 见 `AGENTS.md` §7（单一来源，本指南不重复） | `baseline/requirements-v1.0` |

## 6. 结构变更流程

1. 提出变更（飞书或口头）→ 配置经理受理并登记变更记录；
2. 评审（涉及交付物目录的需项目经理参加）；
3. 通过后：配置经理执行目录调整 → 更新本指南版本号 → 同步 `AGENTS.md` §6 总览树 → 打基线 tag。
