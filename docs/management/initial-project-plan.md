## 2 项目概述与建设目标

### 2.1 项目背景

校园讲座、竞赛和社团活动通常需要协调场地、设备、工作人员及审批。活动时间与资源可用情况相互制约：同一场地可能被多个活动申请，设备需要按可用数量分配，布场与撤场也会占用资源。活动改期后，原有预约、人员安排和报名信息需要同步处理。

教师和学生对具体资源的申请资格还可能存在差异。例如，一间会议室可以设置为仅允许教师申请，另一间活动室可以同时允许教师和学生申请。系统需要将身份资格、业务审批和资源可用性结合起来，准确说明申请能否受理、资源能否预约以及变更影响。

### 2.2 软件建设目标

系统围绕活动全过程建立统一的信息管理与协作流程，使申请人能够查询资源、提出活动申请、查看审核结果并管理本人活动，批准人能够处理授权范围内的申请，管理员能够维护账号、资源和申请资格并完成资源复核。

资源调度同时检查场地容量、开放时段、设备数量和布撤场时间。发生冲突时，系统展示冲突资源、具体时段和数量缺口，并提供按调整偏好排序的备选安排。申请人可以比较时间变化、场地变化和设备替换情况，选择合适方案。

活动改期前展示新旧安排及受影响的资源、审批、工作人员和报名信息；完成必要确认后统一更新相关记录。改期失败时保持原预约记录的一致性，资源故障则单独显示风险。通知和操作记录用于查询处理过程及结果。

### 2.3 课程实践目标

1. 完成需求分析、系统建模、数据库设计、编码、集成和测试，形成能够实际运行的软件系统。
2. 将业务要求落实为角色权限、数据结构、模块接口和测试用例，建立需求到实现的对应关系。
3. 通过并发、越权、重复提交和异常回滚等场景，验证资源占用与业务数据的一致性。
4. 按照六个课程岗位开展协作，形成任务分配、成果交接、评审修改和版本管理记录。
5. 使课程文档与软件版本保持一致，成员能够说明本人承担的设计、实现和验证工作。

### 2.4 总体技术方案

系统由浏览器前端、应用服务和数据库组成。前端提供角色工作台、活动页面、资源日历、方案对比和改期操作；后端完成认证授权、业务规则检查、资源调度及事务处理；数据库保存账号、资源资格、活动版本、审批、预约、报名、通知和审计数据。

后端采用单体应用并按业务模块划分，模块之间通过统一接口协作。活动、资源和改期模块共用身份认证、错误处理和重复请求处理机制。预约、释放及资源切换通过统一调度入口完成，相关数据在同一事务中保持一致。

## 3 系统角色与功能要求

### 3.1 角色身份与业务关系

系统设置申请人、批准人、管理员三类角色。角色决定账号能够执行的操作，教师或学生身份用于判断资源申请资格。教师身份与批准权限分别设置；一个账号可以经授权兼具角色，执行每项操作时仍须检查授权范围和记录归属。

| 系统角色 | 业务职责 | 数据与操作范围 |
| --- | --- | --- |
| 申请人 | 查询资源，创建和管理活动申请，查看审批与预约结果，发布活动，发起改期或取消 | 管理本人创建的申请；按教师或学生身份使用符合资格的资源；学生可报名和退出已发布活动，查看本人参与记录 |
| 批准人 | 审核活动申请及改期申请，记录批准或驳回意见 | 处理授权组织及资源类别范围内的待审批事项，查看完成审核所需的信息 |
| 管理员 | 维护账号、身份、角色授权、资源及申请资格，登记故障，复核资源并查询运行记录 | 按具体管理权限维护账号或资源；对管理范围内的资源完成首次预约确认和改期资源确认 |

活动创建者承担该活动的组织职责，并从本组织启用账号中指定工作人员。工作人员通过活动成员关系获得对应改期的确认权限，能够查看本人需要确认的安排及处理结果。报名人员查看本人报名记录并接收活动变更通知。

申请审核和资源最终复核由申请人之外的授权账号执行。批准人处理业务审批，管理员处理资源复核，两项操作分别记录。账号具有多种角色时，仍遵守本人申请回避、数据归属和管理范围约束。

### 3.2 资源申请资格与权限控制

每个场地或设备资源分别设置教师申请资格和学生申请资格。管理员维护资源资格，申请人身份取自账号资料，系统据此判断申请资格。前端展示可申请资源及受限原因，后端独立完成相同校验。

| 资源资格设置 | 教师申请人 | 学生申请人 |
| --- | --- | --- |
| 同时允许教师和学生申请 | 可提出申请 | 可提出申请 |
| 仅允许教师申请 | 可提出申请 | 提示资格受限并拒绝提交 |
| 仅允许学生申请 | 提示资格受限并拒绝提交 | 可提出申请 |
| 两类身份均关闭申请 | 拒绝新增申请 | 拒绝新增申请 |

同一活动申请的场地和设备均须满足申请人的身份资格。资格检查覆盖申请提交、备选方案生成、改期申请及资源最终确认，防止通过替换资源或直接调用接口绕过限制。

资源资格调整后，新申请及尚未完成资源确认的申请按最新资格校验；已经生效的预约继续保留。已预约活动再次申请改期时，按最新资格检查目标资源。资格变更记录操作者、时间及修改内容；资源故障通过故障记录和影响提示处理。

### 3.3 功能模块

| 模块 | 主要功能 |
| --- | --- |
| 账号与权限管理 | 登录、退出、账号启停、教师与学生身份维护、三类角色授权、审批及管理范围设置、数据归属检查 |
| 活动申请管理 | 创建与编辑草稿，填写时间、人数、场地和设备需求，指定工作人员，提交与撤回申请，查询进度，发布及取消活动 |
| 审批管理 | 待办查询、申请查看、批准与驳回、意见记录、改期复审，审批结果关联具体申请版本 |
| 资源管理 | 场地与设备资料、容量与库存、开放时段、身份申请资格、故障登记及受影响活动查询 |
| 联合调度 | 资源日历、布撤场占用计算、场地与设备整体预约、冲突解释、备选方案生成与比较 |
| 报名与人员协作 | 学生报名及退出、容量检查、本人参与记录、工作人员指定及改期确认 |
| 活动变更 | 改期预览、新旧安排对比、影响清单、人员确认、复审、资源复核与安排切换 |
| 通知与审计 | 申请与审批结果通知、改期及取消通知、通知已读、失败重试、操作记录与历史追溯 |

备选方案以目标时间前后两小时为搜索范围，按30分钟间隔调整开始时间，保持活动时长及布撤场时间。候选组合包括原设备组合，以及将其中一项设备需求替换为同类资源的组合，全部资源均须满足申请人的资格。系统最多检查300个组合并展示最多5个可行方案，依次按时间偏移的绝对值、场地变化和设备替换项数排序，页面说明各方案的调整内容及搜索结果。

### 3.4 主要业务流程

申请人查询资源后填写活动信息并保存草稿。提交时，系统校验身份资格、时间、人数、资源及人员信息，将申请交给授权批准人。批准人同意后进入资源待确认状态；管理员重新检查资源资格和实际可用情况，场地与设备均满足条件时建立联合预约。预约生效后，申请人发布活动并开放学生报名。

审批中的申请保持资源未占用状态。资源最终确认发生冲突时，系统保留申请及审批记录，显示冲突原因；申请人调整安排并重新提交相应版本。备选方案用于辅助选择，实际占用以资源最终确认结果为准。

已预约活动改期时，申请人先预览新旧安排及影响，再提交选定方案。除申请人本人外，被指定的工作人员逐人确认；全部同意后由批准人复审，随后由管理员进行资源最终复核。没有其他待确认工作人员时，申请直接进入复审。任一人员拒绝或审批驳回后，本次改期结束并保留原因。

资源复核通过时，系统在同一事务中建立新活动版本、释放旧预约、生成新预约并更新有效报名关联，同时保存审计记录及待投递通知事件。通知投递失败后单独重试，已经提交的活动安排保持生效。资源冲突时记录改期失败并保留原版本及预约；业务事务执行异常时整体回滚。原资源存在故障时，原记录同时显示风险，便于申请人继续处理。

活动尚未开始时允许申请改期或取消，改期目标开始时间应晚于提交时刻。学生报名和退出以活动已发布且尚未开始为条件；待处理改期期间暂停该活动的报名和退出，改期结束后按活动状态恢复操作。取消活动时统一关闭待处理改期、释放预约、取消有效报名，并向相关人员发送通知。通知已读与工作人员确认分别记录。

### 3.5 数据与一致性要求

活动包含一个主场地和一个连续时段，资源占用覆盖活动开始前的布场及结束后的撤场。相邻占用区间端点相接时可以连续使用资源；设备按同一时刻的总需求检查库存，故障数量从该时刻可用数量中扣除。

数据设计分别保存账号身份、角色授权和资源申请资格，保留活动版本、审批版本及改期目标之间的关联。审批通过的内容与资源确认的内容应一致，申请内容改变后生成相应新版本。并发预约、报名和取消操作通过事务及锁控制，避免资源超额、人数超限和记录不一致。

接口采用统一的请求、响应和错误结构。后端检查角色、资源资格和数据归属，返回可理解的失败原因。相同请求重复提交时返回一致的处理结果；活动、预约、通知和审计数据能够在刷新页面及服务重启后保持一致。

## 5 开发过程与任务分解

### 5.1 开发过程

项目采用迭代开发方式，按需求与基础准备、主流程实现、变更协同和系统完善逐步形成可运行版本。第一周完成主要业务规则与原型，第二周开展基础功能开发，第三周形成申请至取消的完整主流程，第四周完成改期协同和系统联调，第五周集中回归、修复与整理。

需求分析、原型设计和测试设计同步开展。每个业务模块按照规则确认、接口设计、编码、自测和集成的顺序推进，开发过程中及时更新对应文档。并发、事务、权限等关键处理在模块阶段验证，并在联调阶段复核完整业务结果。

### 5.3 关键依赖与集成顺序

第一周优先统一三类角色、申请人身份、资源资格、审批范围及共享数据定义。数据库结构、接口说明、页面字段和测试数据采用相同定义，避免各模块分别解释同一业务规则。

第二周交付认证权限、活动与资源基础接口，以及通知审计事件入口。活动和资源模块据此接入审批、预约与事件记录；前端同步接入登录、资源查询及草稿页面。

第三周完成申请提交、批准、联合预约、发布、报名和取消的整体联调。第四周在主流程基础上完成工作人员确认、改期复审、资源切换及通知展示，并验证资源被抢占、人员拒绝和执行异常等分支。

接口交付延迟时，项目经理及时拆分受影响任务，安排规则整理、组件实现和可独立执行的测试，并为接口联调重新确定完成时间。公共接口修改后，由涉及的模块共同检查调用结果。

### 7.2 设备与环境安排

成员使用个人计算机开展开发，配置经理在第一周核对开发工具、数据库连接及容器运行条件，记录统一运行方式。测试经理建立固定数据和初始化步骤，使同一用例能够在相同条件下重复执行。

开发、自动化测试与演示环境分别使用独立的数据配置。集成测试采用PostgreSQL验证实际数据库约束与事务行为；时间相关用例使用固定测试时间，普通业务运行使用实际时间。测试环境保留失败日志与必要截图，便于定位问题。

完整部署由数据库、后端和前端三个服务组成。第四周执行安装、初始化和启动演练，第五周按最终版本再次复现。配置经理准备数据库备份与恢复步骤，并检查恢复后的活动、预约、报名和通知记录。

### 7.3 资料与配置管理

源代码、接口说明、数据库迁移、模型源文件、课程文档和测试数据统一纳入版本管理。成员在各自模块分支完成修改，交接时附带版本及检查结果；集成版本由项目经理协调，配置经理记录对应代码、文档和运行配置。

需求与设计完成阶段评审后保存对应基线，后续修改记录原因及影响。数据库结构变更通过新增迁移文件实施，保持已有环境可以按顺序更新。配置经理定期备份配置库，并在最终版本整理时核对文件完整性。

账号口令、令牌和数据库凭据通过环境配置管理。日志及报告保留问题定位所需信息，演示和测试使用专门数据。个人通知、报名名单与审批意见按授权范围提供查询。

## 8 质量保证与测试安排

### 8.1 质量目标与检查措施

系统质量重点覆盖业务正确性、权限有效性、数据一致性、界面可用性和运行可复现性。需求阶段核对角色、身份、资源资格与业务流程；设计阶段核对数据关联、接口条件和事务边界；编码阶段检查输入校验、错误处理和模块自测；集成阶段核对页面、接口与持久化结果。

关键设计和文档由其他成员交叉检查，意见记录到具体内容及版本。涉及权限、预约和改期切换的修改，由业务负责人和测试经理共同复核。公共工程及模块合并前完成构建与相应测试，保留执行结果。

### 8.2 测试阶段与方法

| 阶段 | 时间 | 验证重点 | 记录内容 |
| --- | --- | --- | --- |
| 工程与环境检查 | 第1周 | 后端构建、数据迁移、前端构建、初始化及测试工具 | 环境版本、执行入口和检查结果 |
| 单元与模块测试 | 第2至3周 | 权限、资源资格、活动状态、调度约束、重复请求 | 输入、预期、实际结果及对应模块 |
| 集成与系统测试 | 第3至4周 | 活动主流程、改期、通知、并发、事务及页面交互 | 用例结果、数据库检查、问题与证据 |
| 回归与运行检查 | 第5周 | 缺陷复验、核心流程复测、策略评测和部署复现 | 回归结果、评测数据及测试报告 |


### 8.3 重点检查内容

| 检查项 | 操作场景 | 预期结果 |
| --- | --- | --- |
| 角色与数据权限 | 申请人查看他人私有记录，批准人处理范围外申请，管理员执行未授权管理操作 | 请求被拒绝，业务数据保持原状态，页面说明原因 |
| 身份与资源资格 | 教师和学生分别申请同一受限会议室，并通过接口重复尝试 | 申请结果符合具体资源设置，前端提示与后端校验一致 |
| 资格变更与备选方案 | 修改资源资格后处理待确认申请、查询备选方案和提交改期 | 未确认申请与目标资源按最新资格检查，已生效预约保留，备选方案满足申请人资格 |
| 本人申请回避 | 兼具批准或管理权限的申请人审核、复核本人活动 | 自审和本人资源复核被拒绝，由其他授权账号处理 |
| 申请版本与审批 | 编辑、提交、驳回、撤回及再次提交，使用旧版本执行操作 | 版本与状态转换正确，审批结果绑定对应内容，旧版本请求被拒绝 |
| 联合预约 | 场地可用但设备不足，两个活动同时竞争同一空闲场地 | 失败申请无部分占用；竞争时最多一个活动成功预约该场地 |
| 时间与数量边界 | 相邻时段、布撤场重叠、设备错峰占用及资源故障 | 以完整占用区间和同时需求计算，容量及库存约束正确 |
| 报名容量 | 容量为1时20个学生同时报名，成功者重复报名后退出 | 有效报名人数始终不超过1，重复报名不增加人数，退出后名额恢复 |
| 改期确认与切换 | 工作人员同意或拒绝，批准人复审，管理员确认资源 | 状态按顺序变化；同意后统一切换安排，拒绝后保留原有效版本及预约 |
| 改期冲突与异常 | 预览后资源被其他活动占用，切换过程中注入测试异常 | 冲突保留原安排并说明原因，执行异常使相关数据整体回滚 |
| 取消与重复请求 | 取消与改期确认同时发生，同一请求重复提交 | 取消生效后资源释放、报名关闭，重复请求不重复改变数据或生成通知 |
| 通知与持久化 | 通知首次投递失败后重试，用户已读，页面刷新和服务重启 | 每个事件对同一收件人只有一条通知，已读不改变确认意见，重启后业务记录一致 |


### 8.4 缺陷管理与质量判定

测试经理统一登记缺陷，记录版本、环境、复现步骤、期望及实际结果、严重程度和负责人。缺陷依次经过登记、确认、修复、复验和关闭；复验同时检查原问题及受影响的相邻流程。

造成系统无法启动、越权访问、数据丢失、资源重复占用或关键流程中断的问题列为优先处理项。最终版本应完成全部核心流程和重点检查，严重缺陷关闭，其他问题具有明确处理结论。测试报告记录实际执行的用例及结果，并与对应软件版本关联。

性能测试记录请求规模、设备环境和实际响应时间。发现明显等待、超时或失败时，定位数据库查询、资源锁及前端请求等环节并完成复测。项目经理结合测试结果安排机动工时，保证关键业务问题优先解决。

### 8.5 文档质量

需求、原型、设计、接口说明、测试和用户手册统一项目名称、三类角色、申请人身份及业务术语。需求变更后同步检查数据结构、页面、测试预期和操作说明，保持各材料之间的对应关系。

文档正文采用正式课程报告表述，明确计划任务、责任人和检查方法。图表具有清晰标题，模型保留可编辑源文件，测试结论具有对应记录。定稿时核对章节、目录、编号、排版及软件版本，保证内容完整且前后一致。

## 9 项目管理与变更控制

### 9.1 进度与沟通管理

项目经理维护统一任务清单，记录任务编号、负责人、计划完成周次、预计与实际投入、依赖和成果状态。成员每次交付更新进展，周中集中处理接口与环境问题，周末核对实际完成量并安排下一周工作。

关键依赖延迟超过一个工作日，或任务预计投入较原估算增加20%以上时，负责人及时说明原因、影响及剩余工作。项目经理协调相关成员，调整任务顺序、安排协助或使用机动工时，并同步修改受影响任务的计划。

涉及角色权限、审批规则、资源资格和数据结构的讨论形成决定记录，明确执行人及完成时间。会议记录、评审意见和个人工作记录与相应任务关联，各成员按课程要求记录实际参与情况。

### 9.2 需求与变更管理

需求或接口调整由提出人说明变更内容、原因及涉及功能，系统分析员分析业务影响，设计师核对数据与接口，测试经理确定复测范围，相关开发人员估算工作量。项目经理组织确认后更新任务计划，配置经理登记版本。

三类角色、教师与学生身份、资源申请资格及审批范围作为统一业务定义维护。变更涉及多个模块时，同步更新需求说明、接口、数据库迁移、页面和测试数据，由各负责人完成对应修改并验证调用关系。

变更完成后，由测试经理组织受影响流程复验，配置经理记录变更前后版本及检查结果。项目经理依据实际完成情况关闭任务，使每项调整均能够追溯到原因、实现及验证记录。
