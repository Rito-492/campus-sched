## 1. 任务分解的唯一来源：开发任务包 v2.0

**任务分解不再由本表维护**，以仓库根的开发任务包为唯一基线：

| 文件 | 内容 |
|---|---|
| `agent.md` | 总任务书：产品边界、六人开发分工、依赖与交接、启动指令 |
| `agents/common/01…05` | 五份公共契约：开发基线 / 数据与接口契约 / 验收与演示数据 / 协作与集成规程 / 界面规范 |
| `agents/<学号>-<岗位>.md` | 六份个人任务书，编号任务 PM-01…05、AN-01…05、DS-01…05、QA-01…05、CM-01…06、UI-01…06 |

查某人某阶段做什么：读其个人任务书；查模块/目录归谁：读 `agents/common/04-协作与集成规程.md` §1；查验收标准：读 `agents/common/03-验收与演示数据.md`（D-AT-01…24）。

> **变更历史**：v0.1（2026-09-25）的 P0–P6 文档阶段分解基于"首轮只写文档、编码另行分配"的旧方案；v2.0 任务包明确"六岗位各自承担开发模块、M0–M4 里程碑推进"，旧分解作废。任务包本身的修改属跨模块契约变更，走 `agents/common/02-数据与接口契约.md` §7 规程，由项目经理协调。

## 2. 文档流转与基线流程（各岗位通用）

1. 负责人按个人任务书完成任务，产物提交至所属目录（路由见 `docs/configuration/repo-structure.md` §4），更新本人 `docs/<岗位目录>/handoff.md`；
2. 项目经理组织评审，记录评审意见与结论；
3. 修订闭环后，配置经理打基线 tag（如 `baseline/requirements-v1.0`）并登记基线清单；
4. 已进基线的文档/契约修改必须走变更流程（变更申请 → 评审 → 更新基线）；契约类修改同时声明影响的 API-ID、DTO、表、端口与调用方；
5. 交付物状态变化同步本表 §0，飞书任务看板流转至下一负责人。
