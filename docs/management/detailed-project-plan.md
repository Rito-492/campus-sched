# 新版六人开发执行计划 v3.0

编制日期：2026年10月13日。项目：校园活动协同与资源调度系统。适用课程：软件综合实践。

## 1 开发起点

本轮基于 main 的 `a28dcee` 开始。先同步 main，再在各成员固定分支开发；不从旧成员分支整体覆盖 main。活动分支已有状态机仅可按新版契约检查后选取代码。main 已有测试支撑和自动化测试，但后端基础工程、数据库迁移、前端产品工程尚未完成，已有测试不代表产品已通过验收。

新版任务包由根目录 `taskbook.md`、`agents/common/` 五份公共文件和六份个人任务书组成，整体版本为 v3.0。用户已明确采用新版，旧任务包不再作为执行输入；历史版本保留在 Git 历史中。产品需求依据为软件需求规约 v1.1、用例规约、补充规约、业务规则和用户界面说明。

采用三个软件角色：申请人、批准人、管理员。教师／学生是账号身份，工作人员是活动关系。批准人按组织及资源类别授权；管理员按账号管理、资源管理、资源复核、审计查询权限授权。所有者不能审批或复核自己的申请。资源分别设置教师和学生申请资格。

## 3 执行顺序与验收门槛

计划沿用五周课程周期，以本轮实际开工为第1周；具体课程截止日期由项目经理核实。下表是安排目标，不是已完成状态。

| 阶段 | 建议周次 | 六人可并行的工作 | 集成门槛 |
|---|---|---|---|
| M0 工程基础 | 第1周 | PM共享工程与类型；DS迁移；CM数据库/种子；AN状态机；QA数据和支撑；UI工程和组件 | 同一main版本后端可编译、schema可迁移、前端可构建、测试数据可导入；新版契约检查通过 |
| M1 模块实现 | 第2周 | 账号授权；活动/报名；资源资格/调度；事件/改期；前端页面；跨模块测试 | 每个模块有真实实现与本模块测试；无生产Mock、无第二套认证或工程 |
| M2 首次预约闭环 | 第3周前半 | 登录→创建→提交→审批→管理员资源确认→发布→学生报名→取消 | UI调用真实接口；资格、范围、自审回避、资源竞争及报名容量验证通过 |
| M3 改期闭环 | 第3周后半至第4周 | 冲突/候选→影响→工作人员确认→复审→最终资源切换→通知 | 更新版本/预约/报名/审计/outbox同一事务；冲突保护与异常回滚有数据库证据 |
| M4 回归和交付 | 第5周 | 修复缺陷、UI检查、策略评测、文档核对、干净环境部署和答辩演练 | D-AT-01～24、N-AT-01～06均有真实结果；严重缺陷关闭；报告和发布版本一致 |

首批交接顺序：PM公共类型与构建、DS迁移、CM数据库环境、QA数据共同落地；随后CM优先交EventPort和独立ChangePortAdapter，AN交ActivityPort，DS交SchedulingPort，再推进主流程。端口相互依赖要用独立适配器解除循环，不能以允许循环依赖配置掩盖设计问题。

## 5 完成判定

任务只有在代码、规定检查、交接记录均存在时才标完成。handoff写真实基准、变更清单、命令和通过/失败/阻塞、证据及下一接收人。依赖未到时先做独立逻辑与测试，列明缺少的文件和负责人。

共享文件按common协作规程归属修改；成员提交前先同步main，合并后接收方重新运行相关检查。各人使用自己的Git姓名和已绑定邮箱。不得一键提交所有文件、混入别人未提交的Word修改、把合成测试夹具称为产品验收数据。
